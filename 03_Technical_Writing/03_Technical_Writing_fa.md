# هنر نگارش فنی: از کامنت‌های کد تا راهنماهای کاربر

بیایید واقع‌بین باشیم: شما برنامه‌نویس شگفت‌انگیزی هستید. می‌توانید سیستم‌های پیچیده را معماری کنید، الگوریتم‌ها را بهینه‌سازی کنید، و مشکل‌سازترین باگ‌ها را رفع کنید. اما وقتی نوبت به توضیح کارتان به دیگران می‌رسد؟ آن موقع است که همه چیز به هم می‌ریزد.

به عنوان کسی که سال‌ها مستندات نوشته‌ام - از مستندات API که برنامه‌نویسان دوست دارند تا READMEهایی که واقعاً خوانده می‌شوند - آموخته‌ام که نگارش فنی درباره نثرهای فانتزی نیست. درباره وضوح، همدلی، و ملاقات با خوانندگان دقیقاً جایی است که هستند.

## درک مخاطب: سفر خواننده

بزرگترین اشتباهی که نویسندگان فنی مرتکب می‌شوند این است که فرض می‌کنند همه مانند آنها فکر می‌کنند. کد برلیان شما ممکن است برای شما واضح باشد، اما برای تازه‌واردها، یک هزارتو است.

### چهار پرسونای خواننده
**مدیر اجرایی:** تصویر بزرگ را در ۳۰ ثانیه می‌خواهد. "این چه کاری انجام می‌دهد و چرا باید اهمیت داشته باشد؟"
**برنامه‌نویس:** جزئیات پیاده‌سازی نیاز دارد. "چگونه این را در کد خود ادغام کنم؟"
**کاربر نهایی:** مراحل عملی می‌خواهد. "چگونه این را برای مورد استفاده خود کارآمد کنم؟"
**مشارکت‌کننده:** می‌خواهد درک کند و تغییر دهد. "چگونه کار می‌کند تا بتوانم آن را بهبود دهم؟"

### اصل همدلی
پیش از نوشتن یک کلمه، از خود بپرسید: خواننده‌ام چه چیزی را از قبل می‌داند؟ چه کاری می‌خواهد انجام دهد؟ چه موانعی ممکن است با آنها روبرو شود؟

## ساختار: قانون طلایی نگارش فنی

نگارش فنی عالی از ساختار قابل پیش‌بینی پیروی می‌کند که خوانندگان را از طریق پیچیدگی هدایت می‌کند. آن را همچون GPS برای مغز خواننده تصور کنید.

### سلسله‌مراتب اطلاعات
۱. **بررسی کلی:** این چیست و چرا مهم است (۲-۳ جمله)
۲. **مفاهیم کلیدی:** دانش پس‌زمینه ضروری (لیست‌های نقطه‌دار)
۳. **چگونگی کارکرد:** توضیح اصلی (مرحله‌به‌مرحله یا مفهومی)
۴. **استفاده عملی:** مثال‌های کد، دستورات، اسکرین‌شات‌ها
۵. **مسائل رایج:** عیب‌یابی و مشکلات پنهان
۶. **مراحل بعدی:** چه چیزی یاد بگیرید یا انجام دهید

### فرمت قابل پویش
- **عناوین:** واضح، توصیفی، سلسله‌مراتبی
- **لیست‌ها:** نقطه‌دار برای مفاهیم، شماره‌دار برای توالی‌ها
- **بلوک‌های کد:** با برجسته‌سازی نحو و توضیحات
- **تصاویر:** نمودارها، فلوچارت‌ها، اسکرین‌شات‌ها در صورت مفید بودن
- **فضای سفید:** فضای تنفسی برای چشمان خواننده

## سبک نگارش: واضح، مختصر، دلسوزانه

### چک‌لیست وضوح
- **صدا فعال:** "تابع نتیجه را محاسبه می‌کند" در برابر "نتیجه توسط تابع محاسبه می‌شود"
- **کلمات ساده:** "استفاده کنید" به جای "به کار گیرید"، "نمایش دهید" به جای "ارائه دهید"
- **جمله‌های کوتاه:** ایده‌های پیچیده را بشکنید
- **واژگان ثابت:** از کلمات یکسان برای مفاهیم یکسان استفاده کنید

### نفرین دانش
شما سیستم خود را از داخل و خارج می‌شناسید. خوانندگان شما نمی‌شناسند. اختصارات را توضیح دهید، چیزی را فرض نکنید، و سؤالات را پیش‌بینی کنید.

### قدرت مثال‌ها
فقط توضیح ندهید - نشان دهید. مثال‌های کد، خروجی‌های خط فرمان، و سناریوهای دنیای واقعی مفاهیم انتزاعی را ملموس می‌کنند.

## READMEها: اولین تأثیر پروژه شما

README شما اغلب تنها مستندی است که مردم می‌خوانند. آن را مهم جلوه دهید.

### بخش‌های ضروری
**عنوان پروژه و تگ‌لاین:** نام واضح و یک جمله توصیف
**بج‌ها:** وضعیت ساخت، نسخه، مجوز، دانلودها (از shields.io استفاده کنید)
**بررسی کلی:** چه کاری انجام می‌دهد و چرا مهم است
**نصب:** مراحل راه‌اندازی گام‌به‌گام
**استفاده:** مثال‌های پایه و موارد استفاده رایج
**مشارکت:** چگونه دیگران می‌توانند کمک کنند
**مجوز:** شرایط قانونی استفاده

### روان‌شناسی README
مردم READMEها را در الگوی F پویش می‌کنند: در سراسر بالا، سپس پایین سمت چپ. اطلاعات مهم خود را جایی قرار دهید که چشمان به طور طبیعی می‌روند.

## مستندات API: صحبت برنامه‌نویس به برنامه‌نویس

مستندات API جایی است که نگارش فنی با مهندسی دقیق تلاقی می‌کند.

### سه‌گانه مستندات API
**مرجع:** هر نقطه پایانی، پارامتر، و فرمت پاسخ
**راهنماها:** چگونه وظایف رایج را انجام دهید
**مثال‌ها:** کد کاری که برنامه‌نویسان می‌توانند کپی-پیست-تغییر دهند

### توصیف نقطه پایانی API
- **هدف:** چه کاری انجام می‌دهد؟
- **پارامترها:** نوع، مورد نیاز/اختیاری، فرمت، مثال‌ها
- **پاسخ‌ها:** موارد موفقیت و خطا
- **احراز هویت:** چه اعتبارنامه‌هایی مورد نیاز است

## پیام‌های خطا: هنگامی که همه چیز اشتباه می‌شود

پیام‌های خطا آخرین شانس شما برای کمک به کاربران است. مستندات خطای ضعیف منجر به تیکت‌های پشتیبانی می‌شود؛ مستندات خطای عالی کاربران را توانمند می‌کند تا مشکلات را خودشان حل کنند.

### فرمول پیام خطای خوب
۱. **چه اتفاقی افتاد:** توصیف مشکل واضح
۲. **چرا مهم است:** تأثیر بر کاربر
۳. **چه کاری انجام دهید:** مراحل بعدی خاص
۴. **پیشگیری:** چگونه در آینده اجتناب کنید

**بد:** "خطای سرور داخلی ۵۰۰"
**خوب:** "اتصال به پایگاه داده شکست خورد. کلید DATABASE_URL محیطی خود را بررسی کنید و اطمینان حاصل کنید سرور پایگاه داده در حال اجراست. راهنمای عیب‌یابی را برای مسائل رایج اتصال ببینید."

## کامنت‌های کد: آینده خود شما سپاسگزار خواهد بود

کامت‌ها فقط برای دیگران نیستند - برای خود شما شش ماه دیگر که نمی‌تواند به یاد آورد چرا آن الگوریتم پیچیده را نوشتید.

### اصول کامنت‌گذاری
- **چرا نه چه:** کد چه کاری را نشان می‌دهد؛ کامنت‌ها توضیح می‌دهند چرا
- **هدف و زمینه:** چه مشکلی را حل می‌کردید؟
- **فرضیات:** چه شرایطی باید درست باشد؟
- **هشدارهای آینده:** محدودیت‌های شناخته شده یا TODOها

## ابزارهای حرفه‌ای: بهتر بنویسید، سریع‌تر بنویسید

### تولیدکنندگان مستندات
- **OpenAPI/Swagger:** مستندات از مشخصات API تولید کنید
- **Slate:** مستندات زیبا، پاسخگو
- **ReadMe:** پلتفرم مستندات تعاملی
- **MkDocs:** ساده برای سایت‌ها

### ابزارهای نگارش
- **Markdown:** منبع قابل خواندن که به HTML تبدیل می‌شود
- **Grammarly:** بهبود نگارش و سبک
- **Hemingway App:** تحلیل خوانایی
- **Draw.io یا Mermaid:** نمودارها

### چک‌لیست خودبررسی

## نتیجه‌گیری: مستندات به عنوان محصول

مستندات API شما فقط محصول جانبی API شما نیست - خود محصول است. تعهد شما به تجربه برنامه‌نویس و کیفیت فرهنگ مهندسی شما را منعکس می‌کند.

هر بار که برنامه‌نویس با موفقیت API شما را ادغام می‌کند، به این دلیل است که مستندات شما او را راهنمایی کرد. هر بار که مبارزه می‌کند، به شما بستگی دارد که بهبود دهید.

در مستندات خود همچون کد خود سرمایه‌گذاری کنید. بازده‌ها - رضایت کاربر کاهش یافته، هزینه‌های پشتیبانی، ارزش محصول - سرمایه‌گذاری را فراتر خواهد برد.

API شما ممکن است قدرتمند باشد، اما مستندات شما است که آن را قابل دسترسی می‌کند. آن را مهم جلوه دهید.
